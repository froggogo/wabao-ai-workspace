## 二、业界主流实现方式调研

### 2.1 四种主流路线对比

| 路线 | 做法 | 命中率 | 准确率 | 成本 | 适用 |
| --- | --- | --- | --- | --- | --- |
| **A. 关键词规则库** | 正则 / 关键词触发固定话术 | 低（15~30%） | 高（命中即对） | 极低 | 兜底层，不能单独用 |
| **B. 语义缓存（Semantic Cache）** | Query 向量化 → 相似度超阈值 → 直接返回历史答案 | 中（25~55%） | 依赖阈值 | 低（仅 embedding） | **重复问题的最佳解** |
| **C. RAG 检索增强生成** | 检索知识库 → 拼 Prompt → LLM 生成 | 高（可覆盖长尾） | 中高（有幻觉风险） | 高（每次调 LLM） | 长尾与复杂咨询 |
| **D. Agent + 工具调用** | LLM 自主调用订单/物流/库存 API | 高 | 中 | 最高（多轮迭代） | 需要实时业务数据的场景 |

### 2.2 调研得到的关键事实

**语义缓存阈值是全局最重要的旋钮**（来源：Portkey 基于 2.5 亿次缓存请求的实践、Respan 2026 生产指南、Spheron 基准）：

| 相似度阈值 | 客服场景命中率 | 误答率（FP） |
| --- | --- | --- |
| 0.99 | 1~3% | < 0.1% |
| 0.97 | 5~10% | ~0.5% |
| **0.95** | **15~25%** | **1~3%** |
| **0.93** | **25~40%** | **3~7%** |
| 0.90 | 35~55% | 7~15% |
| 0.85 | 45~70% | 15~30% |

> 行业共识：**首次上线用 0.95~0.97 起步**，建立评测回路后再逐步下探到 0.93。绝不能凭直觉设阈值，需要 ≥300 组历史问答对做 PR 曲线标定。

**纯向量检索在电商场景会翻车**（来源：多篇电商 RAG 实战复盘）：订单号、SKU、快递单号、型号这类实体，向量检索准确率极差，必须叠加关键词/精确匹配。混合检索（向量 + BM25/关键词）可把准确率从 74% 提升到 82%。

**RRF（Reciprocal Rank Fusion）是多路召回融合的事实标准**：`score = Σ 1/(k + rank)`，`k = 60`，规避不同检索器分数尺度不可比的问题。

**pgvector + HNSW 是 2026 年 1000 万向量以内的默认选择**：`m=16, ef_construction=64` 起步，`halfvec`（FP16）量化可省一半存储、召回损失可忽略，`ef_search` 运行时按会话调优。不需要引入 Milvus / Qdrant 这类额外组件。

**分层缓存是标配**：精确匹配层（Redis，零误答）→ 语义层（向量）→ LLM 兜底。

**影子模式（Shadow Mode）是安全上线的必经之路**：先只记录「本可以命中」的日志而不真正发送，用真实流量验证准确率后再放开自动发送。

### 2.3 别人的坑（直接规避）

1. 过度依赖向量检索，对订单号/SKU 的精确匹配需求效果极差。
2. 命中率高但误答被掩盖 —— 需要单独监控**未命中路径的 P99 延迟**和**命中的误答率**，而不是只看平均值。
3. 多租户未隔离导致跨店铺串答 —— 缓存键必须包含 `tenant_id` / `shop_id`。
4. TTL 一刀切 —— 时效性内容（促销、库存、物流时效）必须短 TTL 或禁止缓存。

## 三、方案选型结论

### 3.1 一句话结论

> 采用 **「精确缓存 → 规则/实体 → 语义回答池 → RAG 生成 → 转人工」的五级漏斗**，以**语义回答池（Answer Pool）为主力**承接重复问题，RAG 只做长尾兜底；全链路先跑**影子模式**，达标后按店铺灰度放开自动发送。

### 3.2 关键技术选型

| 决策点 | 选型 | 理由 |
| --- | --- | --- |
| 向量存储 | **pgvector 0.8+（halfvec + HNSW）** | 已有 Postgres 16；FAQ 量级（万级条目、十万级变体）远未到 pgvector 上限；事务内可与业务表 JOIN，运维零新增 |
| 关键词检索 | **pg_trgm + 自建别名/关键词表** | 中文/泰语/越南语的 Postgres 原生 FTS 分词质量差；trgm + 人工同义词表更可控。未来量大再引入 ParadeDB（`pg_search`）做真 BM25 |
| 融合算法 | **RRF（k=60）** | 免分数标定 |
| Embedding | **抽象 Provider，起步用 `text-embedding-3-small`（1536 维）** | 多语言够用、便宜（$0.02/M tokens）；预留 **BGE-M3** 自托管选项（东南亚小语种更强，且原生支持稠密+稀疏混合） |
| Rerank | **阶段一不上**；阶段三引入 `bge-reranker-v2-m3` | 回答池条目短、召回集小，先用阈值分档 + LLM 校验足够 |
| 队列 | **BullMQ + 已有 Redis** | 平台 Webhook 有 3s / 500ms 硬超时，必须「秒 ACK + 异步消费」 |
| 精确缓存 | **Redis（规范化文本 SHA256）** | 零误答、亚毫秒 |
| LLM | 复用现有 `AiService`，新增便宜档模型路由 | FAQ 类走小模型，复杂推理才走大模型 |

### 3.3 为什么不是「直接上 RAG + 大模型」

1. **成本**：跨境客服日均消息量大，每条都过 LLM，token 成本是语义缓存的 50~100 倍。
2. **延迟**：语义命中 50~200ms，LLM 生成 1~3s，买家体验差异明显。
3. **可控性**：回答池的答案是**人工审核过的确定文本**，平台合规风险可控；LLM 生成的内容存在幻觉与违规风险，跨境平台对客服话术有硬性规定。
4. **可运营**：运营同学能直接看到、编辑、下线某一条回答；LLM 的行为无法精确干预。

> RAG + LLM 不是不用，而是**降级为长尾兜底 + 草稿建议**，且默认不自动发送。

## 五、核心机制：五级命中漏斗

每条买家消息按顺序穿过以下层级，**任一层命中即短路返回**。

### L0 · 精确缓存层（Exact Cache）

- **做法**：文本规范化（去空白、统一全半角、小写、去 emoji、去标点）→ SHA256 → Redis 查 `cs:exact:{shopId}:{lang}:{hash}`。
- **命中率**：15~25%（跨境客服的原话重复率很高，如 "how long is shipping?"）。
- **延迟**：< 5ms。
- **误答率**：0。
- **TTL**：按答案类型分级 —— 政策类 7 天、物流时效类 12 小时、促销/库存类不缓存。
- **写入时机**：L2/L3 产出并成功发送后回写。

### L1 · 规则与实体层（Rule & Entity）

- **实体抽取**：正则 + 词典抽取订单号、SKU、快递单号、金额、日期。
  - Shopee 订单号形如 `2xxxxxxxxxxxxxx`（纯数字/字母数字混合）
  - Mercado Libre `pack_id` / `order_id` 为纯数字
- **命中实体 → 走工具调用**（不走回答池）：
  - `query_order`：订单状态
  - `query_logistics`：物流轨迹
  - `check_stock`：库存
- **命中关键词黑名单 → 直接转人工**（见第九节）。
- **要点**：这一层的存在就是为了解决「向量检索对精确实体无能为力」这个已知坑。

### L2 · 语义回答池层（Answer Pool）★ 主力

```
用户问题
   │
   ├──► 语言识别（franc / CLD3）→ 得到 lang
   │
   ├──► Embedding（多语言模型，跨语言可对齐）
   │
   ├──► 并行两路召回（限定 scope：站点 + 店铺 + 全局）
   │      ├─ 向量召回 top-20（pgvector HNSW，cosine）
   │      └─ 关键词召回 top-20（pg_trgm + 别名词表）
   │
   ├──► RRF 融合（k=60）→ top-5
   │
   └──► 阈值分档决策
          ├─ sim ≥ 0.95  →  直接自动回答（高置信）
          ├─ 0.88 ≤ sim < 0.95  →  生成建议，人工一键采纳（中置信）
          └─ sim < 0.88  →  落入 L3
```

**分档策略是本方案的安全核心**：不是「命中/未命中」二值，而是三档，中间档转化为人工提效而非自动发送。

### L3 · RAG 生成层

- 检索知识库文档（平台政策、商品手册、店铺规则）top-3。
- 拼装 Prompt（含店铺人设、语言要求、禁止事项），调 LLM 生成。
- **默认不自动发送**，产出为「AI 草稿」供客服编辑。
- 只有在「店铺开启激进模式 + 意图在白名单 + 出站审核通过」三个条件同时满足时才自动发送。

### L4 · 转人工

- 生成结构化交接卡片：识别到的意图、抽取的实体、检索到的候选答案、买家历史。
- 触发条件：黑名单意图、连续 2 次未命中、买家明确要求人工、情绪负面。

## 六、回答池数据模型设计

### 6.1 设计要点

1. **一条回答 = 1 个「答案条目」+ N 个「问法变体」+ M 个「语言版本」**。这是回答池区别于普通 FAQ 表的核心：同一个语义（如"多久发货"）在 8 个站点有 8 种语言表达，且每种语言下有多种问法。
2. **向量挂在「问法变体」上，不挂在答案上**。检索的是问法，返回的是答案。
3. **答案支持变量模板**，运行时用订单/商品数据填充。
4. **生效范围（scope）分三级**：全局 → 平台/站点 → 店铺。店铺级覆盖全局级。
5. **每条都有独立的置信阈值覆盖**，敏感条目可单独调高。

### 6.2 Prisma Schema（新增部分）

```prisma
// ============ 平台接入 ============

enum CsPlatform {
  shopee
  mercadolibre
}

enum ShopAuthStatus {
  active
  expired
  revoked
  error
}

model ShopAccount {
  id             String         @id @default(cuid())
  userId         String         @map("user_id")
  platform       CsPlatform
  // Shopee: shop_id；Mercado Libre: seller user_id
  externalShopId String         @map("external_shop_id")
  shopName       String         @default("") @map("shop_name")
  // Shopee: SG/MY/TH/VN/PH/BR/TW/ID；MELI: MLB/MLA/MLM/MLC
  siteId         String         @map("site_id")
  defaultLang    String         @default("en") @map("default_lang")
  // AES-256-GCM 加密后的密文，绝不明文落库
```

### 6.3 向量列的处理

Prisma 不原生支持 `vector` 类型，采用「`Unsupported` 声明 + 原生 SQL 查询」：

```prisma
model AnswerVariant {
  // ...上面的字段
  embedding Unsupported("halfvec(1536)")?
}
```

配套 SQL 迁移（放在 `apps/api/prisma/sql/`）：

```sql
-- 001_enable_pgvector.sql
CREATE EXTENSION IF NOT EXISTS vector;
CREATE EXTENSION IF NOT EXISTS pg_trgm;

-- 002_answer_variant_vector.sql
ALTER TABLE cs_answer_variants
  ADD COLUMN IF NOT EXISTS embedding halfvec(1536);

-- HNSW 索引：m=16 / ef_construction=64 起步
-- 注意 opclass 必须与查询运算符匹配：halfvec_cosine_ops <=> 
CREATE INDEX IF NOT EXISTS idx_answer_variants_embedding
  ON cs_answer_variants
  USING hnsw (embedding halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- 关键词召回用的 trigram 索引
CREATE INDEX IF NOT EXISTS idx_answer_variants_question_trgm
  ON cs_answer_variants
  USING gin (question gin_trgm_ops);

-- 过滤字段的复合索引，避免 HNSW 过滤后的召回悬崖
CREATE INDEX IF NOT EXISTS idx_answer_variants_entry_lang
  ON cs_answer_variants (entry_id, lang, enabled);
```

> **halfvec 的价值**：存储与索引内存减半，召回损失可忽略，且支持最高 4000 维（`vector` 类型上限 2000 维），为将来换更大维度的 embedding 留出空间。

### 6.4 混合检索 SQL（RRF 融合）

```sql
-- 参数：$1=query_embedding, $2=query_text, $3=shop_account_id, $4=lang, $5=site_id
WITH vec AS (
  SELECT v.id, v.entry_id,
         ROW_NUMBER() OVER (ORDER BY v.embedding <=> $1::halfvec) AS rank
  FROM cs_answer_variants v
  JOIN cs_answer_entries e ON e.id = v.entry_id
  WHERE v.enabled
    AND e.status = 'published'
    AND (e.scope = 'global'
         OR (e.scope = 'site' AND e.site_id = $5)
         OR (e.scope = 'shop' AND e.shop_account_id = $3))
  ORDER BY v.embedding <=> $1::halfvec
  LIMIT 20
),
kw AS (
  SELECT v.id, v.entry_id,
         ROW_NUMBER() OVER (ORDER BY similarity(v.question, $2) DESC) AS rank
  FROM cs_answer_variants v
  JOIN cs_answer_entries e ON e.id = v.entry_id
  WHERE v.enabled
    AND e.status = 'published'
    AND (e.scope = 'global'
         OR (e.scope = 'site' AND e.site_id = $5)
         OR (e.scope = 'shop' AND e.shop_account_id = $3))
    AND v.question % $2
  ORDER BY similarity(v.question, $2) DESC
  LIMIT 20
)
SELECT COALESCE(vec.entry_id, kw.entry_id) AS entry_id,
       COALESCE(1.0 / (60 + vec.rank), 0) + COALESCE(1.0 / (60 + kw.rank), 0) AS rrf_score,
       vec.rank AS vec_rank,
       kw.rank  AS kw_rank
FROM vec
FULL OUTER JOIN kw ON vec.id = kw.id
ORDER BY rrf_score DESC
LIMIT 5;
```

> RRF 只用于**排序**。最终是否自动发送，仍以 **top1 的原始 cosine 相似度**与阈值比较为准 —— RRF 分数没有绝对语义，不能直接当置信度。这一点极其重要。

**scope 过滤会引发 HNSW 的「召回悬崖」**：当过滤条件把绝大多数行排除时，HNSW 遍历到的候选可能全被过滤掉。对策：pgvector 0.8+ 开启迭代扫描 `SET LOCAL hnsw.iterative_scan = relaxed_order;`，并设 `hnsw.max_scan_tuples`。

### 7.1 Shopee（虾皮）

#### 权限前置（**必须最先做，会卡进度**）

| 事项 | 说明 |
| --- | --- |
| Chat API 权限 | **需单独申请**：登录 Open Platform → 提交 ticket 说明用途 → 审批通过后才能看到 Chat API 文档 |
| App 类型 | 第三方服务商 → 创建 **Customer Service** 类型 App；自有卖家 → **Seller In House System** |
| 沙箱 | `openplatform.sandbox.test-stable.shopee.sg` |

> **风险提示**：Chat API 审批周期不可控（通常数天到数周），必须在项目启动第一天就提交申请，否则整个项目会被阻塞。

#### 认证与签名

```
partner_id + partner_key（HMAC-SHA256）
  → 卖家授权跳转 → code
  → 换取 shop 级 access_token + refresh_token

access_token 有效期约 4 小时，refresh_token 约 30 天
→ 需要定时任务提前刷新（建议到期前 30 分钟），刷新失败告警
（具体时长以官方文档为准，代码里按接口返回的 expire_in 计算）

请求签名 base string = partner_id + api_path + timestamp + access_token + shop_id
sign = HMAC-SHA256(base_string, partner_key)
```

#### 关键接口

| 用途 | 接口 |
| --- | --- |
| 配置推送 | `v2.push.set_app_push_config`（callback_url + `set_push_config_on: [10]`） |
| 拉取会话列表 | `v2.sellerchat.get_conversation_list` |
| 拉取消息 | `v2.sellerchat.get_message` |
| **人工回复** | `v2.sellerchat.send_message` |
| **自动回复** | `v2.sellerchat.send_autoreply_message` |
| 补偿丢失推送 | `v2.push.get_lost_push_message` + `v2.push.confirm_consumed_lost_push_message` |

#### 合规红线（**直接影响方案设计**）

Shopee Chat API 使用条款明确规定：

1. **禁止**主动的订单状态推送、促销群发。
2. **必须用正确的接口做正确的事**：自动回复走 `send_autoreply_message`，人工回复走 `send_message`，**不得把自动消息伪装成人工消息，反之亦然**。
3. 聊天数据只能用于回复买家，不得他用，需遵守数据保护政策。
4. 2025-07-30 起 `send_message` / `send_autoreply_message` 启用消息校验机制，会限制不必要的消息。

> **设计落点**：`AnswerEngine` 输出必须携带 `sender` 标记（`seller_auto` / `seller_human`），Adapter 据此**路由到不同的 Shopee 接口**。这不是可选项，是硬约束。同时对同一会话的连续自动回复设上限（建议 ≤2 条），避免触发消息校验限制。

#### Webhook 处理

- Shopee 要求 **3 秒内返回 2xx**。
- 推送**只告知"有变化"**，需要再调 API 拉取完整内容。
- 验签：请求头 `Authorization` = `HMAC-SHA256(url + "|" + request_body, partner_key)`。
- 失败推送用 `get_lost_push_message` 补偿；另外配置**每 5 分钟一次的对账轮询**兜底。

### 7.2 Mercado Libre（美客多）

#### 两个独立的消息面

这是 MELI 与 Shopee 最大的结构性差异，**必须分开建模**：

| 面 | 场景 | Topic | 特点 |
| --- | --- | --- | --- |
| **Questions（提问）** | 售前，商品详情页公开提问 | `questions` | **公开可见**、重复率极高、**回答池的最佳战场** |
| **Messages（消息）** | 售后，订单维度私信 | `messages` | 绑定 `pack_id`，卖家不能主动发起 |

#### 认证

```
OAuth 2.0（Authorization Code + PKCE）
access_token 约 6 小时
refresh_token 约 6 个月，但为【单次性】——
  每次刷新都会返回新的 refresh_token，旧的立即失效

→ 刷新逻辑必须加分布式锁（Redis），
  并发刷新会导致 refresh_token 被互相作废，店铺掉线
```

> 这是 MELI 集成最常见的生产事故。刷新必须串行化，且刷新结果要原子写库。

#### 关键接口

| 用途 | 接口 |
| --- | --- |
| 查询提问 | `GET /questions/search?seller_id={id}&status=UNANSWERED` |
| 查询单条提问 | `GET /questions/{question_id}` |
| **回答提问** | `POST /answers` → `{ question_id, text }` |
| 拉取售后消息 | `GET /messages/packs/{pack_id}/sellers/{user_id}?tag=post_sale` |
| 不标记已读 | 追加 `&mark_as_read=false` |
| **发送售后消息** | `POST /messages/packs/{pack_id}/sellers/{user_id}?tag=post_sale` |
| 主动发起（ME2） | `GET /messages/action_guide/packs/{pack_id}` → `POST .../option` |

#### 规则约束

1. **卖家不能主动发起对话**。对 Mercado Envíos 2（Fulfillment / Cross docking / Drop off / Flex），必须先通过 action_guide 选择「沟通理由」，否则报 `blocked_by_conversation_started_by_seller`。买家先发起后，卖家可自由回复。
2. **消息会被平台审核**，被 moderate 的消息仍会返回但状态不同。
3. **Webhook 必须在 500ms 内返回 200**，否则平台会**取消该 topic 的订阅**。这是比 Shopee 更严苛的约束。
4. 推送失败会在 1 小时内重试，超时丢弃。
5. 验签：`x-signature` 头（`ts=...,v1=...`），用应用密钥校验。

> **设计落点**：500ms 硬约束意味着 Webhook Controller **绝对不能做任何数据库写入以外的事**，甚至连落库都建议异步。推荐：验签 → `redis.lpush` 原始报文 → 立即 200，落库与拉取全在队列消费者里做。

## 八、检索与相似度工程细节

### 8.1 多语言策略

首批需要覆盖：`zh / en / id / th / vi / ms / pt-BR / es`（Shopee 8 站点 + MELI 拉美）。

**采用「跨语言统一向量空间」而非「每语言一套池」**：

- 用多语言 embedding 模型，中文录入的问法可以匹配到泰语的提问。
- 检索时**不按语言过滤召回**（保留跨语言召回能力），但**答案按买家语言取 `AnswerLocale`**。
- 若目标语言的 `AnswerLocale` 缺失 → 降级为「建议」而非自动发送，同时触发翻译任务补齐。

| Embedding 选项 | 维度 | 多语言 | 成本 | 建议 |
| --- | --- | --- | --- | --- |
| `text-embedding-3-small` | 1536 | 良好 | $0.02/M tokens | **阶段一首选** |
| `text-embedding-3-large` | 3072 | 更好 | $0.13/M tokens | 效果不足时升级 |
| **BGE-M3**（自托管） | 1024 | 优秀（东南亚小语种更强），原生稠密+稀疏混合 | 服务器成本 | 阶段三评估 |

> Provider 抽象 + `embedding_ver` 字段的存在，就是为了支持**换模型时的双写与灰度重建**，避免一次性全量重刷。

### 8.2 阈值标定流程（不可跳过）

```
Step 1  收集 ≥300 组真实历史问答对，人工标注：
        - 正例：不同问法、同一答案
        - 难负例：字面相似但答案不同（如"多久发货" vs "多久到货"）
        
Step 2  跑相似度分布，画 Precision-Recall 曲线

Step 3  取 FP 率 ≤ 1% 的点作为 auto_threshold（预期落在 0.94~0.96）
        取 Recall ≥ 80% 的点作为 suggest_threshold（预期落在 0.86~0.89）

Step 4  上线后每周抽样 100 条命中，人工/LLM-as-judge 复核
        FP 率 > 2% → 阈值上调 0.01
        FP 率 < 0.5% 且持续 2 周 → 阈值下调 0.01

Step 5  「多久到货」这类难负例必须进回归集，每次调阈值都跑一遍
```

**初始默认值**：`auto_threshold = 0.95`，`suggest_threshold = 0.88`。保守起步，绝不激进。

### 8.3 意图识别

两级设计，避免每条消息都调 LLM：

1. **快路径**：回答池检索的 top1 条目自带 `intentKey`，命中即得意图，零额外成本。
2. **慢路径**：L2 未命中时，才用小模型做意图分类（约 20 个预置意图：物流时效、发货状态、退换货、尺码规格、优惠券、发票、地址修改、缺货、投诉、议价……）。

意图的用途不是回答，而是**决定能否自动回复**（见第九节白名单）与**转人工时的路由**。

### 8.4 变量填充

```
答案模板：Hi {{buyer_name}}, your order {{order_no}} was shipped on 
         {{ship_date}}, tracking number {{tracking_no}}. 
         Estimated delivery: {{eta_days}} days.

填充流程：
  1. 解析模板声明的 variables
  2. 从会话上下文 / 订单 API 取值
  3. 任一变量取不到 → 【禁止自动发送】，降级为建议并高亮缺失项
  4. 全部取到 → 渲染 → 出站审核 → 发送
```

> 变量缺失时宁可不发，也不能发出 `your order {{order_no}}` 这种穿帮文本。这类事故在跨境客服里是灾难性的。

## 九、安全闸门与合规红线

### 9.1 硬性不自动回复清单（黑名单，命中即转人工）

| 类别 | 示例 |
| --- | --- |
| 金钱承诺 | 退款、赔付、补偿、折扣议价 |
| 纠纷与投诉 | 开纠纷、要求平台介入、投诉客服、威胁差评 |
| 法律与隐私 | 索要个人信息、发票税务争议、知识产权 |
| 平台外引流 | 买家索要 WhatsApp / 微信 / 私下交易（**Shopee 严禁**，回复不当会被处罚） |
| 敏感内容 | 涉政、色情、暴力、歧视 |
| 情绪极端 | 检测到强烈负面情绪 |

### 9.2 自动回复意图白名单（只有这些才允许自动发）

`shipping.eta`、`shipping.fee`、`order.status`、`product.spec`、`product.stock`、`return.policy`、`payment.method`、`store.hours`、`coupon.usage`、`greeting`

> 白名单是「允许清单」而非「禁止清单」—— 未知意图默认不自动回复。这比黑名单安全得多。

### 9.3 闸门检查顺序

```
候选答案
  │
  ├─ 1. 意图在白名单？          否 → escalate
  ├─ 2. 未命中黑名单关键词？    否 → escalate
  ├─ 3. 相似度 ≥ auto_threshold？ 否 → suggest
  ├─ 4. entry.autoSendEnabled？  否 → suggest
  ├─ 5. 模板变量全部就绪？      否 → suggest
  ├─ 6. 出站内容审核通过？      否 → block + 告警
  ├─ 7. 本会话自动回复数 < 2？  否 → escalate
  ├─ 8. 本店铺分钟级频控未超？  否 → 延迟入队
  └─ 9. 店铺模式 == auto？      否 → shadow / suggest
       ↓
     发送（标记 isAutomated=true）
```

### 9.4 四档运行模式（按店铺配置，支持灰度）

| 模式 | 行为 | 用途 |
| --- | --- | --- |
| `off` | 完全不介入 | 新接入店铺默认 |
| `shadow` | 全链路计算，**只写日志不发送**，客服看不到 | 上线第 1~2 周，验证准确率 |
| `assist` | 生成建议，客服一键采纳/编辑后发送 | 第 3~4 周，验证采纳率 |
| `auto` | 高置信直接发送，中置信仍走建议 | 达标后放开 |

> **灰度路径**：`off → shadow（2 周）→ assist（2 周）→ auto（先 1 个店铺 → 10% → 全量）`。任何指标异常，一键回退到 `assist`。

## 十、闭环：未命中挖掘与自我进化

回答池的价值随时间增长，关键在于**未命中问题能自动变成新条目**。

```
每日定时任务（低优先级队列）
  │
  ├─ 1. 拉取过去 24h 内 layer ∈ {l3_rag, l4_human} 的日志
  │
  ├─ 2. 对 query 做 embedding，跑层次聚类（阈值 0.90）
  │
  ├─ 3. 簇内样本数 ≥ 5 → 生成 UnansweredCluster
  │
  ├─ 4. 对每个簇：
  │      ├─ LLM 归纳代表问题 + 建议意图
  │      ├─ 检索历史人工回答（同簇内客服实际发出的文本）
  │      └─ LLM 综合出候选答案草稿
  │
  ├─ 5. 推送到「待办 FAQ」列表，运营审核
  │
  └─ 6. 审核通过 → 一键转为 AnswerEntry
         ├─ 簇内所有原始问法自动作为 AnswerVariant（source=mined）
         ├─ LLM 扩写 3~5 条同义问法（source=generated）
         └─ 触发多语言翻译补齐 AnswerLocale
```

**另一条进化路径 —— 从人工回答学习**：客服采纳建议时记 `adoptCount`，改写时把改写后的文本作为该条目的优化候选；连续 5 次被改写成相似内容 → 提示运营更新答案。

**衰减机制**：`hitCount` 长期为 0 且创建超 90 天的条目自动标记为「可能过期」，提示下线；`rejectCount / hitCount > 30%` 的条目自动降级为 `autoSendEnabled = false`。

| --- | --- | --- |
| **自动回复率** | 自动发送数 / 买家消息总数 | ≥ 45% |
| **回答池命中率** | (L0 + L2) 命中数 / 总数 | ≥ 55% |
| **误答率（FP）** | 抽样复核中错误的自动回复 / 抽样命中数 | **≤ 1%**（红线） |
| **建议采纳率** | 采纳 + 编辑发送 / 生成建议数 | ≥ 75% |
| **首响时长 P50** | 买家消息到首条回复 | < 10 秒 |
| **转人工率** | escalate / 总数 | ≤ 25% |
| **单条成本** | LLM + embedding 总成本 / 消息数 | ≤ ¥0.01 |
| **未命中路径 P99** | L3/L4 路径的端到端延迟 | < 5 秒（单独监控，不被高命中率掩盖） |

### 14.2 必须单独监控的项

1. **误答率**是唯一红线指标，超过 2% 立即回退到 `assist` 模式。
2. **未命中路径的 P99 延迟**要单独看 —— 高命中率会把平均延迟拉得很好看，掩盖兜底路径的问题。
3. **相似度分布直方图** —— 如果大量命中都刚好卡在阈值线上（0.950~0.955），说明阈值设置在了危险区间。
4. **平台 token 健康度** —— 到期未刷新、刷新失败的店铺数，MELI 尤其要盯。
5. **Webhook 响应耗时 P99** —— MELI 超过 500ms 会被取消订阅，必须告警。

## 十五、成本估算

以**日均 10,000 条买家消息**、单店铺规模测算：

| 项 | 用量 | 单价 | 月成本 |
| --- | --- | --- | --- |
| Embedding（查询） | 10k/天 × 30 × 约 30 tokens | $0.02/M | ≈ $0.18 |
| Embedding（索引重建） | 5 万变体，月重建 2 次 | $0.02/M | ≈ $0.06 |
| L3 RAG 生成 | 假设 20% 走 LLM，2k tokens/次 | 小模型档 | ≈ $18 |
| 聚类挖掘 | 每日一次批量 | — | ≈ $3 |
| pgvector 存储 | 5 万 × 1536 × 2B（halfvec） ≈ 150MB | 复用现有 PG | $0 |
| Redis | 复用现有 | — | $0 |

**月总成本 ≈ $22（约 ¥160）**，单条消息 ≈ ¥0.0005。

对照：若全部走 LLM 生成，月成本约 **$90+**，且延迟差 10 倍。回答池方案的成本优势约 **4~5 倍**，命中部分的延迟优势 **20~50 倍**。

## 十六、风险与对策

| 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- |
| **Shopee Chat API 审批不通过或超期** | 项目阻塞 | 中 | Day 0 提交；并行先做 MELI（无需额外审批）验证全链路；准备"卖家自有 App"备选路径 |
| **误答引发买家投诉 / 店铺处罚** | 严重 | 中 | 影子→辅助→自动的三段灰度；白名单意图；误答率红线自动回退；全量决策审计可追溯 |
| **MELI refresh_token 并发刷新导致掉线** | 店铺失联 | **高** | Redis 分布式锁串行化刷新；刷新失败三次告警；保留手动重授权入口 |
| **MELI Webhook 超 500ms 被取消订阅** | 消息丢失 | 中 | Controller 只做验签+入队；压测 P99 < 100ms；订阅状态定时探活；轮询兜底 |
| **多语言答案质量差（泰语/越南语）** | 买家体验差 | 中 | 机器翻译后**必须人工校对**才能标为 published；未校对语言禁止自动发送 |
| **向量检索对小语种召回差** | 命中率低 | 中 | 关键词召回兜底；阶段三评估 BGE-M3；小语种单独标定阈值 |
| **知识过期（政策/促销变更）** | 答错 | 高 | 分级 TTL；时效性条目强制短缓存；条目 90 天未命中自动提示复核；促销类条目带有效期字段 |
| **回答池冷启动没内容** | 上线即无效 | 高 | 用历史客服记录做首批挖掘；预置 50 条跨境通用 FAQ 模板；影子期专门用于攒数据 |
| **平台限流 / 封禁** | 服务中断 | 低 | 按店铺令牌桶；429 指数退避；严格遵守自动/人工接口区分 |
| **Prisma 不支持 vector 导致开发别扭** | 效率 | 低 | `Unsupported` + 原生 SQL 封装在 `RetrievalService` 内部，对上层透明 |
