## 一、需求变更与由此带来的简化

### 1.1 两项变更

| 变更 | 说明 |
| --- | --- |
| **独立项目** | 新建独立仓库 `wabao-cs`，不与 `wabao-ai` 共享代码、数据库或部署。可复用「设计思路」，不复用「代码」 |
| **不自动发送** | 取消一切自动发送路径。系统只产出候选，**人必须点击才发出去** |

### 1.2 「不自动发送」消掉了整套复杂度

这是本次变更最大的收益 —— 原方案里超过一半的工程复杂度是为「自动发送的安全性」服务的，现在全部可以删掉：

| 原方案组件 | 新方案 | 原因 |
| --- | --- | --- |
| 九道安全闸门（白名单/黑名单/频控/连续上限…） | **删除**，降级为 3 条界面提示 | 人是最后一道闸门，比任何规则都可靠 |
| `shadow / assist / auto` 四档灰度模式 | **删除**，只有一种模式 | 本来就等于永久停留在 `assist` |
| 误答率 ≤1% 红线 + 每周抽样复核 | **删除** | 错的建议坐席不会点，不会到达买家 |
| `auto_threshold` 严格标定（300 组标注 + PR 曲线） | **弱化**为经验值 + 持续观察 | 阈值只影响「候选排序」，不再决定「发不发」 |
| Shopee `send_autoreply_message` 与自动/人工接口区分 | **删除**，统一走 `send_message` | 人工审核后发送，本就是人工消息，不存在伪装问题 |
| Webhook 3s / 500ms 硬超时 + 丢推送补偿 + 分布式锁去重 | **降级**为轮询优先，Webhook 变可选优化 | 人工响应本就在分钟级，30 秒同步延迟完全够用 |
| 变量缺失时禁止发送的强校验 | **弱化**为高亮提示 | 坐席自己会看到 `{{order_no}}` 没填 |
| 全量决策审计 `AutoReplyLog` | **简化**为建议采纳日志 | 不需要为自动行为免责举证 |

**实施周期从 8 周压缩到 6 周，核心模块从 12 个减到 7 个。**

### 1.3 但有两件事变得更重要

| 事项 | 为什么 |
| --- | --- |
| **响应速度与交互流畅度** | 坐席是「用户」了。点击后转圈 3 秒，工具就没人用。必须做预生成 + 流式输出 |
| **双向翻译** | 中国坐席看不懂葡语/西语/泰语/越南语。**翻译可能比回答池本身更刚需**，见第七节 |

## 二、产品形态定义

### 2.1 一句话

> 一个**跨平台统一收件箱**，坐席在里面看买家消息、看中文翻译、点一下拿到 2~3 条现成回答、改两个字发出去。

### 2.2 核心用户旅程

```
① 坐席打开工作台
      ↓
② 左侧会话列表：未读、按平台/店铺筛选、显示中文摘要
      ↓
③ 点击某个会话
      ↓  ← 此时建议已【预生成】完毕，秒开
④ 中栏：买家原文 + 中文翻译并排
   右栏：2~3 条候选回答（中文 + 目标语言对照）
      ↓
⑤ 坐席三选一：
   ├─ 直接【采纳】     → 一键发送
   ├─ 【编辑】后发送    → 记录改动，回流优化回答池
   └─ 【重新生成】/【换个说法】/【自己写】
      ↓
⑥ 发送 → 调平台 API → 记录采纳信号
```

### 2.3 明确不做的事

- ❌ 不自动发送任何消息给买家
- ❌ 不主动发起会话（Shopee 禁止促销群发；MELI 卖家不能主动发起）
- ❌ 不做工单系统、不做 CRM、不做营销
- ❌ 一期不做语音、图片理解

## 三、业界参考（浓缩）

完整调研见[前版第二节](./2026-07-31-17_50-智能回答池-虾皮与美客多自动回复-技术方案.md#二业界主流实现方式调研)。对本项目仍然成立的结论：

1. **纯向量检索在电商场景会翻车**。订单号、SKU、快递单号必须靠关键词/正则精确匹配。混合检索（向量 + 关键词 + RRF 融合）把准确率从 74% 提到 82%。
2. **RRF（`score = Σ 1/(60 + rank)`）是多路召回融合的事实标准**，规避分数尺度不可比。
3. **pgvector + HNSW 是千万向量以内的默认选择**（`m=16, ef_construction=64`，`halfvec` 量化省一半内存），无需引入 Milvus / Qdrant。
4. **相似度阈值与命中率的关系**：0.95 → 15~25% 命中；0.93 → 25~40%；0.88 → 40%+。**在人工兜底的场景下，可以直接用 0.85 作为候选展示门槛** —— 因为多召回一条错的候选，成本只是坐席多扫一眼；而在自动发送场景下这会是事故。

> **这是本方案与前版最重要的参数差异**：阈值从「保守的 0.95」放宽到「激进的 0.85」，命中率翻倍，风险由人承担。

5. **成熟的坐席助手（Intercom Fin、Zendesk Copilot）都是多候选并列**，不是给一个答案，而是给几个让人选。

## 四、技术选型

### 4.1 选型表

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 包管理 / Monorepo | **pnpm 10 + Turborepo** | 团队已熟悉 |
| 后端 | **NestJS 11 + TypeScript** | 团队已熟悉；模块化清晰，AI 友好 |
| ORM | **Prisma 6** | 团队已熟悉 |
| 数据库 | **PostgreSQL 16 + pgvector 0.8**（镜像 `pgvector/pgvector:pg16`） | 一个库搞定关系数据 + 向量，运维零新增 |
| 缓存 | **Redis 7 + ioredis** | 建议缓存、翻译缓存、轮询游标、限流 |
| 队列 | **BullMQ** | 消息同步、预生成、挖掘任务 |
| 前端 | **Next.js 15 App Router + React 19** | 团队已熟悉 |
| UI | **Tailwind v4 + shadcn/ui** | 相比上个项目手搓组件，这次直接用 shadcn 提速（收件箱有大量表格/弹窗/命令面板） |
| 数据层 | **TanStack Query**（替代 SWR） | 收件箱有大量乐观更新、无限滚动、轮询，TanStack Query 更合适 |
| Embedding | `text-embedding-3-small`（1536 维），Provider 抽象 | 多语言够用，$0.02/M |
| LLM | Provider 抽象，默认 `gpt-4o-mini` 档 | 改写与翻译都是轻任务，不需要大模型 |
| 流式 | **SSE** | 生成建议时流式输出，感知延迟大幅下降 |
| 部署 | Docker Compose 单机起步 | 坐席工具并发低，不需要 K8s |

### 4.2 为什么不复用 wabao-ai 的代码

1. **领域完全不同**：wabao-ai 是「用户 ↔ AI」的对话工作台，本项目是「买家 ↔ 坐席」的客服系统，`Conversation` / `Message` 语义不一样，强行复用会拧巴。
2. **生命周期不同**：客服系统要跟平台 API 版本走，迭代节奏和 AI 工作台无关。
3. **数据隔离**：店铺 token、买家聊天记录属于敏感数据，独立库更干净，也便于将来单独做合规审计。
4. **可以复用的是设计**：`AiService` 的 Provider 抽象思路、SSE 管线写法、Prisma 建模风格可以照抄，但是**复制代码而非共享包**。

## 五、系统架构

### 5.1 整体链路（拉取驱动）

```
        ┌──────────────── 后台常驻（与坐席无关） ────────────────┐
        │                                                        │
        │   SyncScheduler（每 30s）                               │
        │        │                                               │
        │        ├─ Shopee:  get_conversation_list（增量游标）    │
        │        └─ MELI:    /questions/search + /messages        │
        │        │                                               │
        │        ▼                                               │
        │   IngestQueue → 幂等落库（cs_messages）                  │
        │        │                                               │
        │        ▼                                               │
        │   PrewarmQueue（低优先级）                              │
        │        ├─ 翻译买家消息 → 中文（带缓存）                  │
        │        └─ 回答池检索 → 缓存 top-5 候选                   │
        │           ※ 只做检索，不调 LLM 生成，省钱                │
        └────────────────────────────────────────────────────────┘
                                 │
                                 ▼
        ┌──────────────── 坐席交互（按需触发） ──────────────────┐
        │                                                        │
        │   坐席点开会话                                          │
        │        │                                               │
        │        ├─ GET /suggestions  →  读预热缓存，< 100ms 秒开  │
        │        │      候选 A：回答池原文                         │
        │        │                                               │
        │        └─ 坐席点「个性化 / 重新生成」                    │
        │               │                                        │
        │               ▼  SSE 流式                               │
        │           候选 B：池答案 + 订单上下文 → LLM 改写          │
        │           候选 C：RAG 知识库 → LLM 自由生成               │
        │                                                        │
        │   坐席采纳 / 编辑 / 弃用  →  发送  →  记录信号            │
        └────────────────────────────────────────────────────────┘
                                 │
                                 ▼
        ┌──────────────── 离线闭环（每日） ──────────────────────┐
        │   未命中问题聚类 → LLM 归纳 → 候选 FAQ → 人工审核入池     │
        │   高频编辑的条目 → 提示优化                              │
        └────────────────────────────────────────────────────────┘
```

**关键设计：预热只做检索，不做生成。** 检索一次成本约 $0.0000006，可以对所有未读消息无脑预热；LLM 生成一次约 $0.005，只在坐席真的点了才跑。这样既保证「点开秒有候选」，又不浪费钱在坐席根本没打开的会话上。

## 六、核心机制：按需三档候选

### 6.1 三档候选

| 档 | 名称 | 来源 | 何时出现 | 成本 | 延迟 |
| --- | --- | --- | --- | --- | --- |
| **A** | 池内原文 | 回答池 top1 直出（已填变量） | 相似度 ≥ 0.85 时，**预热已算好** | 仅 embedding | < 100ms |
| **B** | 上下文改写 | 池答案 + 订单/商品/会话上下文 → LLM 改写 | 坐席点「个性化」，或 A 的变量缺失时自动提示 | 1 次小模型 | 1~2s（流式） |
| **C** | 自由生成 | RAG 知识库 + 会话历史 → LLM 生成 | 坐席点「AI 生成」，或无候选 A 时默认提供 | 1 次生成 | 2~3s（流式） |

**默认展示策略**：

```
if 有相似度 ≥ 0.85 的池条目:
    展示 A（最多 3 条，按 RRF 排序）
    右上角提供「个性化改写」按钮 → B
else:
    不展示 A，直接给「AI 生成」入口 → C
    同时展示相似度 0.70~0.85 的「弱相关参考」（折叠，供坐席参考话术）
```

> **0.85 的门槛怎么来的**：这是「候选展示」门槛，不是「发送」门槛。业界数据显示 0.85 阈值下命中率可达 45~70%，误答率 15~30% —— 在自动发送场景这是灾难，但在人工挑选场景，意味着**坐席有 70% 的概率能直接看到可用答案，剩下 30% 扫一眼就跳过**，净收益是正的。上线后按坐席实际采纳率微调。

### 6.2 候选卡片必须携带的信息

坐席要能一眼判断能不能用，所以每条候选都要透明地给出：

```
┌─ 候选 A1 ────────────────────── 匹配度 0.93 ●●●○ ─┐
│ 来源：回答池 #128「发货时效说明」                   │
│ 命中问法：How long is shipping?                    │
│ 近 30 天被采纳 1,284 次，采纳率 91%                 │
├────────────────────────────────────────────────────┤
│ 【中文】您好 João，订单 240815xxx 已于 8 月 15 日   │
│         发出，快递单号 SP123456789，预计 7~12 天送达│
│ 【葡语】Olá João, seu pedido 240815xxx foi enviado │
│         em 15/08, código SP123456789...            │
├────────────────────────────────────────────────────┤
│ [ 采纳并发送 ]  [ 编辑 ]  [ 个性化改写 ]            │
└────────────────────────────────────────────────────┘
```

透明度是坐席信任工具的前提。黑盒给一句话，坐席不敢用。

### 6.3 变量填充

答案模板支持 `{{buyer_name}}` `{{order_no}}` `{{tracking_no}}` `{{eta_days}}` `{{item_name}}` 等变量。

```
渲染流程：
  1. 解析模板声明的变量
  2. 从会话上下文 + 订单 API 取值（走 L1 实体抽取的结果）
  3. 全部取到  → 直接渲染，候选 A 可用
  4. 有缺失    → 在候选卡片里【高亮标红】未填的变量
                 + 提供输入框让坐席手填
                 + 或提示「用个性化改写自动补全」
```

前版是「变量缺失禁止发送」，这里改为「高亮提示 + 手填入口」—— 坐席自己能看到，不需要系统硬拦。

### 6.4 实体抽取（决定要不要查订单）

```
正则 + 词典抽取：
  Shopee 订单号   240815ABCDEFG（数字+字母，14~16 位）
  MELI  pack_id   纯数字 10~13 位
  快递单号        各家格式词典
  SKU / 型号      店铺商品库匹配
  金额 / 日期     通用正则

命中 → 调用工具（query_order / query_logistics / check_stock）
     → 结果注入候选 B/C 的上下文
     → 同时在界面右下角展示「订单卡片」供坐席参考
```

这一层的存在是因为**向量检索对订单号这类精确实体完全无效**，是调研里反复被强调的坑。

## 七、双向翻译（中国坐席的刚需）

### 7.1 为什么这块单独成节

Shopee 主力站点是 BR / TH / VN / ID / MY / PH，Mercado Libre 是 BR / AR / MX。**中国坐席团队里几乎没人懂葡语、西语、泰语、越南语。**

现实中大量卖家的工作流是：复制买家消息 → 粘贴到 Google 翻译 → 看懂 → 中文写回复 → 再粘回翻译 → 复制结果 → 粘回平台。一条消息切换 4 次窗口。

**把这个流程收进工具里，价值可能超过回答池本身。** 而且它对回答池有正反馈：坐席用中文写的回复，天然就是回答池的中文主语言语料。

### 7.2 设计

```
【入站翻译】
买家消息（pt-BR）
    │
    ├─ 语言识别（franc / CLD3，纯本地，零成本）
    ├─ 查翻译缓存（Redis，key = sha256(text)，命中率 30%+，客服问题重复率高）
    └─ 未命中 → LLM 翻译 → 写缓存
    │
    ▼
界面并排显示：原文 + 中文译文（可折叠原文）

【出站翻译】
坐席用中文写回复
    │
    ├─ 点【翻译并预览】
    ├─ LLM 翻译成买家语言（带电商客服语境 Prompt）
    └─ 【双语对照预览】← 关键：坐席能看到自己要发出去的原文长什么样
    │
    ▼
确认 → 发送目标语言文本
```

### 7.3 翻译质量要点

| 要点 | 做法 |
| --- | --- |
| 术语一致 | 维护店铺级术语表（商品名、品牌名、物流商名不翻译或固定译法），注入 Prompt |
| 保留变量 | 翻译时 `{{order_no}}` 这类占位符必须原样保留，Prompt 里明确约束 + 后校验 |
| 语气 | Prompt 指定「电商客服，礼貌、简洁、不过度承诺」 |
| 不用 MT API | 实测成本反直觉：Google Translate 约 $20/百万字符，10k 消息/天 ≈ $600/月；**用小模型 LLM 翻译只要 $20/月**，且能带语境和术语表 |
| 缓存 | 同一段文本只翻一次，Redis 永久缓存（文本不变则译文不变） |

### 7.4 回答池的语言组织

```
中文 = 主语言（坐席录入、编辑、检索都用中文）
其他语言 = 译文（机器翻译 + 人工校对）

┌────────────────────────────────────────┐
│ 条目 #128「发货时效说明」               │
│ ├─ 主语言 zh：订单一般 2 个工作日内发出 │
│ ├─ pt ✅ 已校对                         │
│ ├─ es ✅ 已校对                         │
│ ├─ en ✅ 已校对                         │
│ ├─ th ⚠️ 机翻未校对（发送前会提示）      │
│ └─ vi ❌ 缺失（点击一键翻译生成）        │
└────────────────────────────────────────┘
```

未校对的译文不禁止使用，但候选卡片上打「机翻未校对」标签，让坐席自己判断。

### 7.5 跨语言检索

Embedding 用多语言模型，向量空间跨语言对齐 —— 买家用葡语问 `quanto tempo demora o envio?`，能直接匹配到中文录入的「发货要多久」。**检索时不按语言过滤**，答案再按买家语言取译文。这是多语言回答池的核心技巧。

### 8.2 向量索引迁移 SQL

放在 `apps/api/prisma/migrations/` 或 `prisma/sql/`：

```sql
-- 索引：HNSW cosine，m=16 / ef_construction=64 起步
-- opclass 必须与查询运算符匹配：halfvec_cosine_ops ↔ <=>
CREATE INDEX IF NOT EXISTS idx_variant_embedding
  ON answer_variants USING hnsw (embedding halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);

CREATE INDEX IF NOT EXISTS idx_chunk_embedding
  ON knowledge_chunks USING hnsw (embedding halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- 关键词召回：trigram
CREATE INDEX IF NOT EXISTS idx_variant_question_trgm
  ON answer_variants USING gin (question gin_trgm_ops);

-- 过滤字段，缓解 HNSW 过滤后的召回悬崖
CREATE INDEX IF NOT EXISTS idx_variant_entry_enabled
  ON answer_variants (entry_id, enabled);
```

> **为什么用 `halfvec` 而不是 `vector`**：FP16 存储，索引内存减半，召回损失可忽略；且支持最高 4000 维（`vector` 上限 2000 维），将来换更大维度的 embedding 不用改类型。

## 九、平台接入：轮询优先

### 9.1 为什么改用轮询

前版用 Webhook，是因为自动回复要求秒级响应。**现在坐席响应本来就是分钟级，30 秒的同步延迟毫无感知**，于是可以砍掉一大堆复杂度：

| Webhook 方案要处理的 | 轮询方案 |
| --- | --- |
| 公网 HTTPS 回调域名 + 平台侧验证 | 不需要，内网部署也能跑 |
| Shopee 3 秒 / MELI **500 毫秒**硬超时 | 不存在 |
| MELI 超时会**取消 topic 订阅** | 不存在 |
| 签名校验、重放攻击防护 | 不需要 |
| 丢推送补偿（`get_lost_push_message`）+ 对账轮询 | 轮询本身就是对账 |
| 推送乱序、并发去重分布式锁 | 单线程游标，天然有序 |

**开发量差异**：Webhook 方案约 5~7 人日，轮询方案约 1.5 人日。

阶段四如果确实需要更实时（比如做「新消息桌面通知」），再把 Webhook 作为**加速通道**叠加上去 —— 轮询保留为兜底，两者并存，架构上互不冲突。

### 9.2 轮询设计

```
SyncScheduler（NestJS @Cron，每 30 秒）
   │
   └─ 对每个 status=active 的店铺，投递一个 sync job（BullMQ）
        │
        ├─ Shopee
        │    GET v2.sellerchat.get_conversation_list
        │        参数：last_message_timestamp > cursor，按时间倒序
        │    → 对有新消息的会话，GET v2.sellerchat.get_message
        │
        └─ Mercado Libre
             ① 售前：GET /questions/search?seller_id=X&status=UNANSWERED
             ② 售后：GET /orders/search 拿近期 pack_id
                     → GET /messages/packs/{pack_id}/sellers/{uid}?mark_as_read=false
                     ※ mark_as_read=false 很重要，不能把买家消息误标已读
        │
        ├─ 归一化 → upsert（唯一键去重，重复即跳过）
        ├─ 更新 shop.syncCursor
        └─ 新买家消息 → 投递 prewarm job
```

**频率分级**（省 API 配额）：

| 店铺状态 | 轮询间隔 |
| --- | --- |
| 有未读会话 / 5 分钟内有活动 | 30 秒 |
| 30 分钟内有活动 | 2 分钟 |
| 长时间静默 | 10 分钟 |
| 非营业时段 | 30 分钟 |

### 9.3 Shopee 要点

| 项 | 说明 |
| --- | --- |
| **Chat API 权限** | **必须单独申请**：Open Platform 提 ticket 说明用途，审批通过才能看到文档。第三方服务商建 **Customer Service** 类型 App；自有卖家建 **Seller In House System**。**审批周期不可控，Day 0 必须提交** |
| 认证 | `partner_id` + `partner_key`，HMAC-SHA256 签名。base string = `partner_id + api_path + timestamp + access_token + shop_id` |
| Token | access_token 约 4 小时，refresh_token 约 30 天。定时任务提前 30 分钟刷新（以接口返回的 `expire_in` 为准） |
| 读消息 | `v2.sellerchat.get_conversation_list` / `v2.sellerchat.get_message` |
| **发消息** | `v2.sellerchat.send_message` —— **人工审核后发送属于人工消息，用这个接口是正确的** |
| 合规 | 禁止主动订单推送、促销群发；不得把自动消息伪装成人工消息。**本项目全程人工点击发送，天然合规**，但仍禁止做群发功能 |
| 站点 | 不同站点 API 域名不同（Global / 中国大陆 / 巴西），配置化 |

### 9.4 Mercado Libre 要点

| 项 | 说明 |
| --- | --- |
| 权限 | 标准 OAuth 应用即可，**无需额外审批**，所以**先做 MELI 验证全链路** |
| 认证 | OAuth 2.0（Authorization Code + PKCE），access_token 约 6 小时 |
| **refresh_token 是单次性的** | 每次刷新返回新 token，旧的立即失效。**并发刷新会互相作废导致店铺掉线，这是 MELI 集成最常见的生产事故**。必须加 Redis 分布式锁串行化，刷新结果原子写库 |
| 两个消息面 | **questions**（售前公开提问，重复率极高，回答池的最佳战场）/ **messages**（售后私信，绑 `pack_id`） |
| 回答提问 | `POST /answers` → `{ question_id, text }` |
| 发售后消息 | `POST /messages/packs/{pack_id}/sellers/{user_id}?tag=post_sale` |
| 读消息不标已读 | `GET /messages/packs/{id}/sellers/{uid}?mark_as_read=false` |
| 卖家不能主动发起 | ME2（Fulfillment / Cross docking / Drop off / Flex）必须先走 `action_guide` 选沟通理由，否则报 `blocked_by_conversation_started_by_seller`。**本项目只做「回复」不做「发起」，规避此问题** |
| 消息审核 | 平台会 moderate 消息，被审核的消息状态不同，需在界面标示 |

### 9.6 幂等与限流

| 问题 | 对策 |
| --- | --- |
| 轮询重复拉到同一条消息 | `messages` 表 `@@unique([conversationId, externalMsgId])`，upsert 冲突即跳过 |
| 同店铺任务重叠 | BullMQ `jobId = sync:{shopId}`，去重；`concurrency = 1` per shop |
| 平台限流 | 按 `shopId` 令牌桶；429 指数退避；队列 `limiter` 全局兜底 |
| 队列优先级 | `sync`(高) > `send`(最高) > `prewarm`(低) > `mining`(最低) |

## 十、检索工程细节

### 10.1 混合检索 SQL（RRF 融合）

```sql
-- $1=query_embedding  $2=query_text  $3=shop_id  $4=site_id
WITH vec AS (
  SELECT v.id, v.entry_id,
         v.embedding <=> $1::halfvec AS distance,
         ROW_NUMBER() OVER (ORDER BY v.embedding <=> $1::halfvec) AS rank
  FROM answer_variants v
  JOIN answer_entries e ON e.id = v.entry_id
  WHERE v.enabled AND e.status = 'published'
    AND (e.scope = 'global'
      OR (e.scope = 'site' AND e.site_id = $4)
      OR (e.scope = 'shop' AND e.shop_id  = $3))
  ORDER BY v.embedding <=> $1::halfvec
  LIMIT 20
),
kw AS (
  SELECT v.id, v.entry_id,
         ROW_NUMBER() OVER (ORDER BY similarity(v.question, $2) DESC) AS rank
  FROM answer_variants v
  JOIN answer_entries e ON e.id = v.entry_id
  WHERE v.enabled AND e.status = 'published'
    AND (e.scope = 'global'
      OR (e.scope = 'site' AND e.site_id = $4)
      OR (e.scope = 'shop' AND e.shop_id  = $3))
    AND v.question % $2
  ORDER BY similarity(v.question, $2) DESC
  LIMIT 20
)
SELECT COALESCE(vec.entry_id, kw.entry_id)      AS entry_id,
       1 - COALESCE(vec.distance, 1)             AS cosine_sim,
       COALESCE(1.0 / (60 + vec.rank), 0)
     + COALESCE(1.0 / (60 + kw.rank),  0)        AS rrf_score
FROM vec
FULL OUTER JOIN kw ON vec.id = kw.id
ORDER BY rrf_score DESC
LIMIT 5;
```

**两个必须注意的点：**

1. **RRF 分数只用于排序，不能当置信度**。展示给坐席的「匹配度」必须用 `cosine_sim`（原始余弦相似度），因为 RRF 分数没有绝对语义 —— 只有一路召回时 RRF 最高分是 `1/61 ≈ 0.016`，直接展示会让坐席以为匹配度只有 1.6%。

2. **scope 过滤会触发 HNSW 的「召回悬崖」**：当过滤条件排除了绝大多数行，HNSW 遍历到的候选可能全被过滤光，返回空结果。对策：

```sql
SET LOCAL hnsw.ef_search = 80;
SET LOCAL hnsw.iterative_scan = relaxed_order;  -- pgvector 0.8+
SET LOCAL hnsw.max_scan_tuples = 20000;
```

### 10.2 相似度门槛

| 门槛 | 值 | 作用 |
| --- | --- | --- |
| 候选展示 | **0.85** | ≥ 此值进入候选 A 列表 |
| 弱相关参考 | **0.70** | 0.70~0.85 折叠展示，供坐席参考话术 |
| 丢弃 | < 0.70 | 不展示，直接走 AI 生成 |

**这些是经验起步值，不做严格标定。** 调优依据不是「误答率」，而是**坐席采纳率** —— 如果 0.85~0.90 区间的候选采纳率长期低于 20%，就把门槛提到 0.90；如果坐席频繁抱怨「没候选」，就降到 0.82。数据从 `Suggestion.outcome` 直接统计得出，比人工标注可靠得多。

> 这是人工兜底方案的一个隐藏红利：**采纳率是天然的、零成本的、持续的标注信号**，不需要像自动发送方案那样组织人力做每周抽样复核。

### 10.3 Embedding

| 选项 | 维度 | 成本 | 结论 |
| --- | --- | --- | --- |
| `text-embedding-3-small` | 1536 | $0.02/M | **起步首选**，多语言够用 |
| `text-embedding-3-large` | 3072 | $0.13/M | 效果不足时升级（需改 `halfvec(3072)`） |
| BGE-M3 自托管 | 1024 | 服务器成本 | 泰语/越南语显著更强，量大后评估 |

Provider 抽象 + `answer_variants` 上加 `embedding_ver` 字段（换模型时双写灰度重建，避免一次性全量重刷）。

### 10.4 索引更新时机

```
条目发布 / 变体新增 / 变体文本修改
        → 投递 indexer job（低优先级队列）
        → 批量 embedding（一次最多 100 条，省调用）
        → UPDATE answer_variants SET embedding = ...
```

回答池条目量级预估：万级条目 × 平均 8 个变体 ≈ 8 万向量。halfvec 存储 ≈ 240MB，HNSW 索引常驻内存 ≈ 400MB。单机 Postgres 轻松承载，**远未到需要独立向量库的规模**。

## 十二、闭环：人工回答即标注数据

**这是人工模式相比自动模式的最大结构性优势。** 自动发送方案里，回答池冷启动是个大难题（"上线即无效"是列在风险表里的高概率事件）；人工模式下，坐席每天的正常工作本身就在生产高质量标注数据。

### 12.1 三种信号

| 信号 | 含义 | 用途 |
| --- | --- | --- |
| **adopted**（原样采纳） | 这条答案对这个问法是对的 | 把买家原话加为该条目的新变体（`source=mined`） |
| **edited**（编辑后发送） | 答案方向对但表述需调整 | 记录 diff；同一条目连续 5 次被改成相似内容 → 提示运营更新答案 |
| **skipped**（自己重写） | 池里没有合适答案 | 「买家问题 + 坐席回复」成为候选 FAQ 的原料 |

### 12.2 每日挖掘任务

```
① 拉取过去 24h 内 outcome=skipped 的记录（买家问题 + 坐席实际回复）
② 对买家问题做 embedding，层次聚类（阈值 0.90）
③ 簇内样本 ≥ 3 → 生成 UnansweredCluster
   （门槛比自动方案的 5 更低，因为人工审核把关，宁可多提候选）
④ 对每个簇：
   ├─ LLM 归纳代表问题 + 建议 intentKey
   └─ 综合簇内坐席的实际回复，生成中文答案草稿
      ※ 关键：草稿来自真人写过的话，而不是 LLM 凭空编，质量高得多
⑤ 推送到「待办 FAQ」列表
⑥ 主管审核通过 → 一键转 AnswerEntry
   ├─ 簇内所有买家原话自动成为变体（source=mined）
   ├─ LLM 扩写 3~5 条同义问法（source=generated）
   └─ 触发一键翻译补齐各语言 AnswerLocale
```

### 12.3 冷启动

第 1~2 周回答池是空的，坐席正常人工回复。**这两周产生的数据直接喂给挖掘任务，第 3 周就能自动产出首批 30~50 条候选 FAQ。**

加速手段：
- 导入历史客服记录（如果卖家有导出）批量跑一次聚类
- 预置 40 条跨境电商通用 FAQ 模板（物流时效、退换货、尺码、关税、发票…）
- 从平台已有的自动回复/常用语设置里导入

### 12.4 条目衰减

- `showCount` 长期为 0 且创建超 90 天 → 标记「可能过期」，提示复核
- `skipCount / showCount > 60%` → 自动降级为 `draft`，提示重写
- `editCount / (adoptCount + editCount) > 50%` → 提示「答案需要优化」

`docker-compose.yml` 关键点：

```yaml
services:
  postgres:
    image: pgvector/pgvector:pg16   # 不是官方 postgres 镜像
    environment:
      POSTGRES_DB: wabao_cs
    ports: ["5433:5432"]            # 避开 wabao-ai 的 5432，两个项目可并行开发
    volumes: [pgdata:/var/lib/postgresql/data]
  redis:
    image: redis:7-alpine
    ports: ["6380:6379"]            # 同样避开端口冲突
```

> 端口错开是为了让两个项目能在同一台开发机上同时跑。

## 十七、指标体系

### 17.1 核心指标（全部可从 `Suggestion` 表直接算出）

| 指标 | 定义 | 目标（3 个月） |
| --- | --- | --- |
| **候选覆盖率** | 有 ≥1 条候选 A 的会话 / 总会话 | ≥ 60% |
| **原样采纳率** | `adopted` / 展示候选数 | ≥ 45% |
| **总采纳率** | (`adopted` + `edited`) / 展示候选数 | ≥ 75% |
| **平均编辑距离** | `edited` 记录的 Levenshtein 距离均值 | 持续下降 |
| **单会话处理时长** | 打开会话 → 发出回复 | 相比基线 **下降 ≥ 50%** |
| **首响时长 P50** | 买家消息 → 首条回复 | < 5 分钟 |
| **坐席日处理量** | 人均每日回复会话数 | 相比基线 **提升 ≥ 80%** |
| **单条成本** | LLM + embedding / 消息数 | ≤ ¥0.02 |

### 17.2 采纳率是唯一的北极星

自动发送方案要盯「误答率」这条红线；人工方案完全不同 —— **坐席不点，工具就没价值；坐席一直点，说明建议是对的**。采纳率同时是产品指标、质量指标和阈值调优依据。

因此埋点必须做扎实：每一次候选展示、每一次点击、每一次编辑的 diff，都要落到 `Suggestion` 表。这是整个项目的数据资产。

### 17.3 需要单独盯的运维指标

| 指标 | 告警条件 |
| --- | --- |
| 店铺 token 健康度 | 刷新失败 / 已过期店铺数 > 0（MELI 尤其要盯） |
| 同步延迟 | 平台消息时间 → 入库时间 P95 > 90 秒 |
| 预热命中率 | 坐席点开会话时候选已就绪的比例 < 90% |
| 建议接口延迟 | `GET /suggestions` P95 > 300ms |
| 生成接口首字延迟 | SSE 首 token > 1.5 秒 |

## 十八、成本估算

按**日均 10,000 条买家消息**测算（单个中型卖家团队规模）：

| 项 | 用量 | 月成本 |
| --- | --- | --- |
| 入站翻译（LLM 小模型） | 10k/天 × 约 200 tokens，缓存命中率 30% | ≈ $16 |
| 出站翻译 | 8k/天 × 约 200 tokens | ≈ $13 |
| 检索 embedding（预热） | 10k/天 × 30 tokens | ≈ $0.2 |
| 索引 embedding | 8 万变体，月重建 2 次 | ≈ $0.1 |
| 候选 B/C 生成 | 假设 30% 会话触发，3k/天 × 1000 tokens | ≈ $22 |
| 挖掘聚类 | 每日一次批量 | ≈ $3 |
| pgvector 存储 | 8 万 × 1536 × 2B（halfvec）≈ 240MB | $0 |
| 服务器（2C4G + PG + Redis） | 单机 | ≈ $20 |

**月总成本 ≈ $75（约 ¥540）**，单条消息 ≈ ¥0.0018。

| 方案 | 月成本 | 说明 |
| --- | --- | --- |

**ROI 极其明显**：月成本不到半个坐席人力的 10%，只要人效提升 20% 就回本。

## 十九、风险与对策

| 风险 | 影响 | 概率 | 对策 |
| --- | --- | --- | --- |
| **Shopee Chat API 审批不通过或超期** | Shopee 侧无法接入 | 中 | Day 0 提交；**先做 MELI 打通全链路**，Shopee 作为并行分支；准备"卖家自有 App（Seller In House System）"备选路径 |
| **MELI refresh_token 并发刷新导致店铺掉线** | 店铺失联 | **高** | Redis 分布式锁串行化刷新；刷新失败三次告警；保留手动重授权入口。**这是 MELI 集成的头号事故源** |
| **坐席不用这个工具** | 项目失败 | **中高** | 阶段二先交付翻译（独立有价值、立刻能用）建立使用习惯；做需求访谈；快捷键与秒开体验是硬要求；用采纳率数据驱动迭代 |
| **翻译质量差导致买家误解** | 客诉 | 中 | 双语对照预览让坐席自己把关；店铺术语表；变量占位符后校验；重要话术走人工校对的 locale |
| **回答池冷启动没内容** | 前期无候选 | 高 | 预置 40 条通用 FAQ；导入历史客服记录跑聚类；**阶段一、二的两周本身就在攒语料** |
| **点开会话候选没准备好，转圈** | 体验差 | 中 | 预热队列覆盖所有未读；未就绪时先展示骨架屏 + 走实时检索（也就 200ms）；监控预热命中率 |
| **知识过期（政策/促销变更）** | 建议过时 | 高 | 条目 90 天未展示自动提示复核；促销类条目带有效期字段；`editCount` 高的条目主动提示更新 |
| **多语言译文质量参差（泰语/越南语）** | 建议不可用 | 中 | 未校对译文打「机翻」标签；候选排序上人工校对的优先；小语种优先找兼职校对 |
| **平台限流** | 同步变慢 | 低 | 分级轮询频率；按店铺令牌桶；429 指数退避 |
| **Prisma 不支持 vector 类型** | 开发别扭 | 低 | `Unsupported` 声明 + 原生 SQL 封装在 `RetrievalService` 内部，对上层透明 |
| **候选 0.85 门槛导致噪音过多** | 坐席嫌烦 | 中 | 门槛可配置；按采纳率数据动态调整；最多展示 3 条，弱相关折叠 |
