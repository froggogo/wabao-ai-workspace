## 一、结论速览

| 问题 | 结论 |
| --- | --- |
| 前后端是否分离 | **是，彻底分离**。前端独立应用，后端只提供 REST + SSE API，通过契约（OpenAPI）解耦 |
| 前端 | **Next.js 15（App Router）+ React 19 + TypeScript + Tailwind CSS v4**；数据层统一用 **SWR** |
| 后端主选 | **NestJS（Node.js + TypeScript）** |
| 后端备选 | Python + FastAPI（当 AI/数据处理需求变重时，作为独立微服务补充） |
| 代码组织 | **pnpm monorepo + Turborepo**：`apps/web`、`apps/api`、`packages/shared` |
| 架构演进 | **模块化单体（Modular Monolith）起步 → 按域拆分微服务** |

---

## 二、为什么前后端分离

1. **职责清晰**：前端专注交互与渲染，后端专注业务、编排、安全与计费，各自独立部署与扩容。
2. **独立扩容**：AI 请求是 IO 密集且耗时的，后端可单独水平扩展、加队列；前端走 CDN 静态分发。
3. **多端复用**：同一套 API 未来可服务 Web、桌面、移动、浏览器插件。
4. **契约驱动**：以 OpenAPI/TypeScript 类型为契约，前后端并行开发，AI 也能据契约生成代码。

> 分离 ≠ 割裂：通过 monorepo + 共享类型包，把"接口类型"在前后端间共享，避免联调时的类型漂移。

## 三、后端选型分析

### 3.1 为什么主选 NestJS（TypeScript）

| 维度 | NestJS 的优势 |
| --- | --- |
| **方便 AI 理解** | 与前端**同一门语言（TS）**，全栈统一心智；约定式、装饰器、模块化结构高度规整，AI 生成/续写代码上下文一致，出错率低 |
| **好维护** | 模块（Module）/ 控制器（Controller）/ 服务（Service）/ 提供者（Provider）分层清晰，依赖注入天然解耦，易测试 |
| **好扩容** | 内建模块边界，先做模块化单体，后续可无痛拆为微服务（Nest 原生支持 microservices、gRPC、消息队列） |
| **生态** | OpenAI 官方 Node SDK 一流支持；SSE/WebSocket、校验（class-validator）、Swagger 自动生成开箱即用 |
| **共享类型** | DTO / 接口类型可与前端共享，契约零漂移 |

### 3.2 何时引入 Python + FastAPI（备选/补充）

保留演进空间：当出现**重 AI/数据处理**需求时（如自建向量检索优化、复杂 RAG 管道、Embeddings 批处理、模型微调流水线、数据科学任务），把这类能力做成**独立的 Python 微服务**，通过内部 API 与 Nest 主服务通信。P1 阶段**不需要**。

### 3.3 一句话选型逻辑

> P1~P2 以 TypeScript 全栈（NestJS）统一开发，最大化"AI 友好 + 可维护"；当 AI 计算密集需求出现时，用 FastAPI 微服务补齐，而非一开始就上多语言多服务。

## 四、目标架构

### 4.1 Monorepo 结构

```
wabao-ai/                      # pnpm monorepo 根
├── apps/
│   ├── web/                    # 前端：Next.js 15（App Router）+ React 19 + SWR + Tailwind
│   └── api/                    # 后端：NestJS（P1）
├── packages/
│   ├── shared/                 # 共享类型/DTO/常量（前后端复用契约）
│   ├── ui/                     # (可选) 共享 UI 组件库
│   └── config/                 # 共享 eslint/tsconfig/tailwind 预设
├── pnpm-workspace.yaml
├── turbo.json                  # Turborepo 任务编排与缓存
└── package.json
```

> P1 前端已落地在 `apps/web/`（Next.js 15 App Router + SWR），由早期 `wabao-prototype/` 原型迁移而来。

### 4.2 后端分层（NestJS · 模块化单体）

```
apps/api/src/
├── main.ts
├── app.module.ts
├── modules/
│   ├── auth/          认证（M12）
│   ├── users/         用户与用量（M12）
│   ├── assistants/    助手人设（M1）
│   ├── conversations/ 会话与消息（M1）
│   ├── creations/     创作与模板（M3）
│   └── moderation/    审核（M9，内嵌能力）
├── ai/                # AI 编排层（核心）
│   ├── openai.client.ts   OpenAI SDK 封装
│   ├── router.service.ts  模型路由 Sol/Terra/Luna
│   ├── prompt.service.ts  Prompt 模板管理
│   └── stream.service.ts  SSE 流式封装
├── common/            拦截器/守卫/过滤器/DTO 校验
└── infra/             数据库/缓存/队列/对象存储适配
```

**AI 编排层**是核心竞争力，独立成层，业务模块通过它调用模型，便于统一路由、缓存、审核与计量。

### 4.3 分层调用关系

```
前端(React) --REST/SSE--> API 网关(Nest 守卫/限流/鉴权)
   -> 业务模块(Controller/Service)
   -> AI 编排层(路由/Prompt/流式/审核/计量)
   -> OpenAI Platform
   -> 数据层(PostgreSQL / Redis / 对象存储)
```

## 五、可维护 / 可扩容 / AI 友好的具体做法

### 5.1 可维护
- **统一 TypeScript 全栈**，一套语言、一套 lint/format/tsconfig（放 `packages/config`）。
- **契约先行**：Nest 自动生成 Swagger/OpenAPI，前端据此生成类型客户端。
- **分层与依赖注入**：业务与 AI 调用解耦，便于单元测试与替换。
- **约定式目录**：按功能域（feature）组织，命名规范统一。

### 5.2 可扩容
- **无状态 API + 水平扩展**：会话状态入库，实例可任意扩缩。
- **异步与队列**：耗时任务（长文本、批量创作）走队列 + Webhook。
- **模块边界清晰**：需要时按域拆微服务，改动最小。
- **缓存**：Prompt caching + Redis 缓存热点数据，降本提速。

### 5.3 方便 AI 理解（AI-friendly 工程）
- **单一语言、规整结构**：AI 补全上下文一致，跨前后端无语言切换成本。
- **共享类型包**：AI 修改接口时前后端类型同步，减少幻觉式错配。
- **强类型 + Schema 校验**：DTO/zod/class-validator 让边界明确，AI 易于推断。
- **文档与代码同源**：OpenAPI 契约、README、类型即文档。
